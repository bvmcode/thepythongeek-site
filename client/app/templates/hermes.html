01 / The system

What runs where

I wanted an assistant that could pick up a task after I had closed the conversation. Some of those tasks are personal: record a health reading, send the morning message, or look for new jobs. Others involve the infrastructure behind this website. In all of them, the useful part happens after the agent has worked out what I asked for. It needs a place to save the result, access to the right machine, and a way to tell whether the work finished.

I chose Hermes Agent, the open-source framework from Nous Research. It brings persistent sessions, tools, scheduling, and reusable skills into one environment. The procedures I use repeatedly can be written down as skills and loaded again, so the next conversation has the same deployment steps or recording rules available. I still have to give those procedures working credentials, sensible permissions, and checks that match the task.

The setup has three main machines. Hermes runs on EC2. My Mac supplies the Apple-specific capabilities, including Contacts and Messages, and keeps a CSV copy of my health data. A separate production host runs this site. Tailscale connects the machines privately. Telegram gives me a familiar interface from my phone; the desktop app reaches the agent through the tailnet.

AI News makes a useful walkthrough because it touches nearly every part of that arrangement. The agent writes the briefing, changes a tracked file, works through GitHub, connects to production, and checks the website. The page advertises a daily update at 7pm. That publishing schedule belongs to the agent's automation; Flask's job is to serve the document that reached production.

Below, I follow that update through the system first, then explain how the agent host is provisioned and how the same connections support the smaller daily jobs.

02 / The publishing pipeline

How AI News gets onto the site.

AI News is where the pieces of this setup have to agree with one another. Hermes produces a briefing, Git records it, the production host picks it up, and Flask serves it. A good draft can still fail to reach the website. A perfectly healthy website can still be showing yesterday's draft. I find the system much easier to reason about when I treat those as separate problems.

The durable output is client/app/hermes/ai_news.md: a dated heading, story summaries, and links to their sources. Publishing means replacing that document through the site's existing repository workflow. When somebody opens AI News, the application reads the deployed file. The reader's request does not start an agent session or wait for a model.

One update, from source to readerMarkdown → Git branch → Merged PR → Production checkout → Flask page

1. Give the draft a history

I keep the briefing in Git because the diff answers practical questions. Which stories changed? Did a source link disappear? Was the heading corrected without changing the body? The November 2 update in PR #4 changed only ai_news.md. Later, PR #7 corrected its heading from November 3 to November 2. That small correction is useful evidence: the publication date is part of the content, and it can be wrong even when every infrastructure step succeeds.

The agent works in its own clone, creates a branch, commits the document, and pushes it. Git transport and GitHub's pull-request API use different credentials in this setup: a repository-scoped SSH deploy key handles the push, while the authenticated gh CLI creates the PR and requests squash auto-merge. That separation matters when troubleshooting. A successful push says nothing about whether the CLI can open or merge a pull request.

# Illustrative sequence in the agent's clone; substitute the date and PR number.
git switch -c content/ai-news-YYYY-MM-DD
git add client/app/hermes/ai_news.md
git commit -m "Update AI News for YYYY-MM-DD"
git push -u origin content/ai-news-YYYY-MM-DD

gh pr create --base main --title "AI News: YYYY-MM-DD" \
  --body "Update the daily briefing and source links."
gh pr merge <pr-number> --auto --squash

# Inspect the result before deployment. The required state is MERGED.
gh pr view <pr-number> --json state,mergedAt,mergeCommit

The pause between requesting auto-merge and deploying is essential. Auto-merge can remain pending while repository rules are unsatisfied. During the original setup, commit attribution held a merge open; using my GitHub noreply identity resolved it. The command returning successfully was not proof that main contained the change. I want the actual merge state before asking production to pull anything.

2. Move the merged content onto the production host

The deployment sequence I set up connects over the tailnet and runs ssh mysite 'sh ~/deploy.sh'. That host-side script pulls the repository and runs docker-compose up -d --build. The script lives outside this website repository, so the application checkout is not a complete record of the deployment machinery. What it does contain is the configuration of the services being deployed.

The application image starts from Python 3.11, installs the Python requirements, copies the client directory into /app, and starts uWSGI. Production Compose defines the application, Redis, and nginx services. There is an important detail in the application's volume configuration:

# Relevant excerpt from docker-compose.yml
services:
    app:
      build: .
      volumes:
          - ./client:/app
      expose:
        - 8080

That bind mount makes the host's client directory the running application's /app directory. It takes precedence over the copy baked into the image. For a news-only update, the checked-out Markdown is therefore the content the application reads; rebuilding an image is not inherently necessary just to replace that file. Rebuilding remains part of the established deployment procedure, which also handles application changes. This makes the production checkout part of the release. The image alone does not capture everything a reader will see.

The two network paths also have different jobs. Hermes uses private access to administer the host. Readers arrive at nginx over public HTTPS. The nginx configuration forwards application requests to app:8080 using the uWSGI protocol, while static assets have their own nginx location. uWSGI runs four worker processes with two threads each. Redis is present in the wider site's stack, but the AI News route itself reads a file; it does not ask Redis for the briefing.

On the agent, the deployment invocation and the host inspection are separate commands. Running docker ps on the agent would inspect the wrong Docker daemon. The container check needs to run on mysite; the HTTP check needs to use the public address that readers use.

# From the agent host, after the PR has merged:
ssh mysite 'sh ~/deploy.sh'
ssh mysite 'docker ps'

# News-route diagnostic, beyond the original homepage check:
# Inspect the printed status; this alone does not check freshness.
curl --fail --silent --show-error --output /dev/null \
  --write-out '%{http_code}\n' https://thepythongeek.com/ai-news/

3. Render the document within an explicit boundary

The file path is anchored to the Python module with Path(__file__).resolve().parent, so it does not depend on the process's working directory. The loader decodes UTF-8 and rejects a blank document. After that, the route passes the text to a shared renderer used elsewhere in the site.

# The shared renderer in app/stormy_ai/views.py
rendered = markdown.markdown(
    markdown_text,
    extensions=["extra", "sane_lists"],
)
sanitized = bleach.clean(
    rendered,
    tags=ALLOWED_MARKDOWN_TAGS,
    attributes=ALLOWED_MARKDOWN_ATTRIBUTES,
    protocols=ALLOWED_MARKDOWN_PROTOCOLS,
    strip=True,
)
return Markup(sanitized)

Markdown conversion and HTML sanitization solve different problems. The first supplies headings, lists, links, and tables. The second limits which HTML survives. The allowlist admits presentation elements and selected attributes; link protocols are restricted to HTTP, HTTPS, and mailto. Only the sanitized result is marked safe for Jinja. A test exercises this boundary with a script tag, an image event handler, and a JavaScript link. Sanitization controls browser behavior; it does not establish whether a news claim or its source is trustworthy.

Although that helper lives in the Stormy AI module, AI News does not use Stormy's storage path. Stormy follows an S3 latest.txt pointer to another object. AI News reads the Markdown beside its own view module on each request. Sharing the renderer saves duplicate code without making the two publishing systems identical.

If the file is missing, unreadable, incorrectly encoded, or empty, the news route logs the exception and returns a useful unavailable message with HTTP 503. Its tests cover loading a real document, rendering a supplied Markdown sample, and the missing-file response. Those checks are valuable, but they do not exercise the agent, GitHub, the external deployment script, or the production network.

4. Check availability, then ask a harder question

The original release check inspected running containers and requested the public homepage. That establishes a limited kind of success: the site answered after deployment. I would also request /ai-news/, because a working homepage does not exercise the briefing loader. Even a 200 from the news route is only an availability check. An old, readable Markdown file still produces a successful response.

The next improvement I want is a content check tied to the particular release. Record the expected edition date and merged commit, inspect the deployed checkout, then confirm that the public news page contains the expected edition. The date correction in PR #7 makes this more than a theoretical concern. The intended publication date needs to be explicit, with a defined timezone, instead of inferred from whichever machine happens to run a check.

I also want a documented recovery procedure. Git preserves earlier briefings, but keeping history is not the same as implementing rollback. A deliberate revert through a new PR would fit this workflow; it would still need deployment and the same public-content check. Freshness checks and that recovery procedure are planned improvements, not protections I am claiming the present pipeline already provides.

03 / Provisioning & access

A small server, with a job I can explain

I run Hermes on an Ubuntu 24.04 EC2 instance in us-east-1. It is a t3.medium, with 4 GB of memory and an encrypted gp3 root volume. That is enough for the agent, its gateway, browser tools, and the Ollama client because I am not loading the language model's weights on this machine. The expensive inference happens with a cloud provider.

Ollama listens on 127.0.0.1:11434. Hermes uses its OpenAI-compatible API at /v1, and Ollama forwards requests to the selected cloud model. Keeping the endpoint local makes the configuration convenient; it does not make inference local. Prompts and the context included in those requests still leave the instance. What I operate myself is the process that maintains sessions, reads files, schedules work, and invokes tools.

That separation is useful. I can change the model without moving the health database, rewriting the deployment procedure, or rebuilding the messaging integration. Telegram and the desktop gateway are ways into the same agent environment. My Mac and the production server supply capabilities the EC2 instance does not have on its own.

What Terraform actually rebuilds

The infrastructure repository defines the instance, security group, instance profile, and first-boot install. It selects an Ubuntu 24.04 image, requires IMDSv2 for instance metadata, and encrypts the root disk. I can recreate that machine from configuration. Recreating the machine and restoring its working state are separate jobs: Terraform does not recover my SQLite records, conversations, or credentials.

cd infra
cp terraform.tfvars.example terraform.tfvars && cp backend.hcl.example backend.hcl
terraform init -backend-config=backend.hcl
terraform apply        # ~5-10 min of user-data install on first boot

There is an important gap between the instance existing and the agent being ready. User-data is still installing packages after Terraform finishes. The bootstrap installs Ollama, installs Hermes as the ubuntu user, and enables lingering so that user's services can continue without an interactive login. It also creates a systemd service for the dashboard, configured to restart on failure. The install writes a progress log and a completion marker so I can distinguish “EC2 is up” from “the install finished.”

The dashboard username, password, and signing secret are created on the instance. The password is generated with OpenSSL, and shell tracing is disabled while those values are written. The resulting environment file is owned by ubuntu with mode 0600. Those generated credentials never need to be embedded in the Terraform configuration, state, or user-data template.

SSM gets me in; the tailnet connects the machines

I use AWS Systems Manager Session Manager for an administrative shell on Hermes. The default Terraform configuration has no inbound SSH rule and no EC2 key pair. That does not prevent the agent from making outbound SSH connections. When it needs Messages on my Mac or the deployment script on production, it acts as an SSH client across Tailscale.

The dashboard listens on port 9119. During setup, access is controlled by dashboard_allowed_cidrs; the repository's default is broad, so narrowing it is an explicit setup step. Once the desktop can reach the gateway over the tailnet, I set that list to [] and apply again. That removes the public dashboard ingress rule. The agent still needs outbound access for model APIs, messaging services, and package downloads.

For the Mac, I install a dedicated ed25519 public key in authorized_keys. The production host has its own SSH access, a pinned host key, and the mysite alias. These keys let the agent reach particular machines. The repository deploy key is a different credential: it grants Git access to one repository. The GitHub CLI's OAuth token handles API operations such as creating and merging pull requests. A repo-scoped Git key does not automatically limit that token's permissions, and joining the tailnet does not replace authentication to the services on it.

04 / Everyday workflows

The same setup handles the small, recurring work

Deployments are the most visible example, but they are not the reason I keep the agent running. I also use it for health records, a morning message to my wife, and a daily search for jobs. These are ordinary tasks with enough small details that a half-finished result is more trouble than it is worth.

Health records: SQLite first, a complete CSV copy second

I can dictate a reading in a sentence instead of opening a form. The agent separates the values and writes them to SQLite. The original schema has a daily_readings table for dates, times, weight, glucose, blood pressure, pulse, and notes, plus a meals table for food descriptions and nutrition values. Glucose entries have a constrained category: fasting, before-meal, after-meal, bedtime, or random.

The database schema helps, but it cannot decide whether the agent understood me correctly. SQLite column declarations alone are not a complete validation system. The recording procedure matters too: do not invent a missing measurement, check serving sizes against the nutrition source, and ask when the amount is something only I know. The weight column uses kilograms, so a dictated value in pounds also needs a deliberate conversion rather than a unit silently dropped.

After an insert, a Python sync script exports the full state to ~/Documents/HealthData/ on my Mac. SQLite remains the source of truth. The CSVs are a convenient local copy I can inspect and use elsewhere. I rebuild that copy instead of appending one new line because I sometimes correct old entries. If I change or delete a row in the database, the next complete export reflects it; a simple append would leave the old version behind.

/usr/bin/python3 /home/ubuntu/health_data/health_sync.py
# synced: daily_readings=1, meals=6

This makes repeat runs useful: exporting the same database again should produce the same records, without duplicates caused by the retry. It also gives me two separate outcomes to check. Saving a reading and copying the export to the Mac are different operations; a failed transfer does not mean the database insert failed. The agent's role here is recording and organizing information. I do not ask it to turn those rows into a diagnosis.

Scheduled jobs need a result and a clock

The morning message is scheduled for 6:00 AM. It writes a Bible-verse note to my wife, rotates the selection, signs it “I love you, Barry,” and sends it through the Mac. The job also checks the outgoing message record and runs the health-data sync. At 9:00 AM, the job scout looks for remote senior or lead data-engineering roles with a stated salary of at least $150,000. It checks that postings are live, excludes jobs already sent, and delivers the remaining list to Telegram.

Those times describe the intended local schedule. The original jobs use UTC anchors, so they need adjustment when the local UTC offset changes with daylight saving time. A fixed UTC schedule does not automatically preserve 6:00 AM in New Jersey throughout the year. I want that limitation stated plainly because a job that runs successfully at the wrong hour is still wrong for its purpose.

Telegram is also where failures are meant to surface. For the scout, a smaller list of verified, new postings is more useful than padding the result with repeats. For the morning message, a send command finishing is only one step. The workflow needs to check what the Mac recorded before reporting the outcome.

What the iMessage check proves

The Linux instance reaches my Mac over SSH and uses a small AppleScript to send through Messages. Before sending, it resolves the recipient through Contacts, normalizes the phone number, and selects the one-to-one chat. Finding a group conversation that happens to contain the same person is not enough. For an ad hoc message, the procedure includes confirming the recipient and exact text with me; the morning job uses the recurring instruction I already gave it.

The verification step reads the Mac's Messages SQLite database separately from the send script. It checks the outgoing flag, a recent timestamp, and the exact message text, including decoding attributedBody when the text lives in that serialized field. That is evidence that my Mac recorded the intended outgoing message. It is not evidence from my wife's phone, and it does not prove she received or read it. Keeping that distinction makes the confirmation useful rather than overstated.

Voice is another way to reach the tools

Telegram voice notes are transcribed with faster-whisper in the gateway environment. Spoken replies use OpenAI text-to-speech, with Opus output and the voice selected in configuration. The desktop also has a full-duplex realtime voice session over WebRTC, so I can interrupt while it is speaking.

Those are separate roles: transcription turns audio into a request; speech synthesis turns a response into audio; the realtime session manages a live conversation. Work that needs the shell, files, or another machine goes to the Hermes agent. A spoken request to log a reading or deploy a fix should reach the same procedure and checks as a typed one. The microphone changes how I ask, not what counts as finishing the job.

05 / Operating the system

What I check before calling a job finished

The common thread across these jobs is that each crosses a boundary. A draft moves into Git. A merged commit moves onto another machine. A reading moves from speech into a database, then into a file on my Mac. I get a clearer picture of failures when I check those transitions separately instead of treating a long sequence of commands as one success or failure.

Evidence I can inspect, and what it leaves unanswered
OperationUseful evidenceStill a separate question
Merge a briefingPR state is MERGED; the change is on main.Has production pulled that change?
Deploy the siteHost-side deployment output and running containers.Does the public news page serve the expected edition?
Record a readingThe intended values exist in SQLite.Did the full CSV mirror reach the Mac?
Send a messageExact outgoing text, sender flag, and timestamp on the Mac.Was it received or read on the other device?

Some fixes have been straightforward systems work. The production checkout needed the correct owner, and the deploy user needed Docker access so the script could run without an interactive sudo prompt. That access deserves care: membership in the Docker group is powerful access to the host, even when the command line no longer contains sudo. Removing the prompt solves an automation problem; it does not make the underlying privilege disappear.

The branch-attribution issue taught a similar lesson. Git had accepted a commit, but GitHub's rules still had a reason to hold the PR. Keeping the agent's commit identity attributable made the audit history more useful and let the intended merge workflow work. I want failures like that to remain visible, because they identify the specific boundary that needs attention.

The next improvements

My first priority is the AI News release check: compare the expected edition and merged commit with the deployed checkout and public page. That gives the publishing job a stronger finish line than a successful HTTP response. A documented revert-and-redeploy procedure belongs alongside it. I also want to make the morning schedules follow the intended local timezone through daylight saving changes, and to keep recovery of the agent's working data distinct from recreating its EC2 instance.

Beyond that, I want charts from the health history once there is enough data to make a trend meaningful. The useful foundation is already in place: records I can query, procedures I can inspect, and machines the agent can reach. Each additional job should be small enough to explain in those same terms.
