01 / From draft to production

How AI News gets onto the site.

AI News is the best example of the whole setup working together. Each day's briefing becomes a Markdown file in this site's repository. That file goes through a pull request, a merge, and a deployment before anyone can read it here. Writing the news is only the first part of the job.

Why keep the news in Git?

It makes the update easy to inspect. The November 2 briefing, for example, landed as PR #4 and changed only ai_news.md. I can see exactly what was published and compare it with the previous edition. The news uses the same deployment path as the rest of the site.

What does “healthy” tell me?

If the briefing file is missing, empty, or unreadable, the news route returns HTTP 503 with a useful message. A readable old briefing can still return 200, though. Checking the published date is the next improvement I want to make to the release check.

The commands behind the deployment

A walkthrough of the publishing path, including an explicit merge-state check and a check of the news route. The PR number comes from the newly created pull request.

# In the agent's clone: version the new briefing.
git switch -c content/ai-news-YYYY-MM-DD
git add client/app/hermes/ai_news.md
git commit -m "Update AI News for YYYY-MM-DD"
git push -u origin content/ai-news-YYYY-MM-DD

# Open the PR and request a squash auto-merge.
gh pr create --base main --title "AI News: YYYY-MM-DD" \
  --body "Update the daily briefing and source links."
gh pr merge <pr-number> --auto --squash

# Wait for MERGED. An auto-merge request is not a completed merge.
gh pr view <pr-number> --json state,mergedAt

# Once merged, run the deployment on production.
ssh mysite 'sh ~/deploy.sh'
# The script runs git pull + docker-compose up -d --build.

# Check containers on that host, then check the public news route.
ssh mysite 'docker ps'
curl -sS -o /dev/null -w '%{http_code}\n' \
  https://thepythongeek.com/ai-news/

02 / The setup

One agent, a few connected machines.

I chose Hermes Agent, the open-source framework from Nous Research, because it combines tools, persistent memory, scheduling, and reusable skills. I wanted to give a job to the same agent from my phone or my Mac and have it keep the context.

Hermes runs on a Terraform-provisioned EC2 instance. Tailscale connects it to my Mac and the production server. Telegram is a messaging interface to the gateway; the desktop app reaches it over the private network.

The agent's private access to production is separate from the public website readers visit.

Provisioning
Terraform and first-boot setup install the agent. The instance uses an encrypted gp3 volume and requires IMDSv2.
Administration
SSM Session Manager provides shell access to the agent host. Public SSH is disabled.
Dashboard
Initial access is limited by allowed CIDRs. After Tailscale is working, that public allowlist is emptied.
Deployment access
A repository-scoped Git key, GitHub CLI authentication for PRs, and a separate SSH connection to the production host.
Provisioning the instance 
cd infra
cp terraform.tfvars.example terraform.tfvars
cp backend.hcl.example backend.hcl
terraform init -backend-config=backend.hcl
terraform apply

First-boot installation takes about five to ten minutes. The infrastructure is in bvmcode/my-hermes-agent.

03 / Everyday use

The smaller jobs matter, too.

Most of my interactions with Hermes are fairly ordinary. I give it a reading, ask it to send a message, or read the list it found while I was doing something else. These are the jobs that made the setup worth keeping.

A health log I use

Dictate → SQLite → CSV

I can say my blood pressure, glucose, or weight in a sentence. Hermes puts the readings into typed SQLite fields and keeps meals in a separate table. Values come from me or a verified nutrition label; missing quantities need a question, not an estimate quietly added to the record.

After an entry, a sync script sends a full CSV copy to my Mac. Rebuilding the copy means a corrected or deleted row makes it across, too. That detail matters much more to me than saving a few seconds by appending to yesterday's export.

The morning message

Daily / 6:00 AM

Each morning it sends my wife a note with a Bible verse, signed “I love you, Barry.” The Linux agent reaches my Mac over Tailscale and sends through AppleScript. Contacts supplies the recipient, and the bridge resolves the one-to-one conversation before sending.

A separate check reads the Mac's Messages database for the exact text, an outgoing flag, and a recent timestamp. That confirms the outgoing message is recorded on my Mac; it doesn't tell me whether she has read it.

The daily job scout

Daily / 9:00 AM

The scout looks for remote senior and lead data-engineering roles with a stated salary of at least $150K. It checks that the postings are still available, removes roles it has already sent, and delivers the remaining list to Telegram. Failed scheduled jobs also report there.

The morning jobs use UTC-based schedule anchors. Their local times need attention when daylight saving time changes.

Talking to it

Phone & desktop

Telegram voice notes are transcribed with faster-whisper, and replies can use text-to-speech. On the desktop, a realtime voice session lets me interrupt and follow up naturally. Requests that need tools go to the same Hermes agent that handles the scheduled work.

04 / Field notes

A few things I had to get right.

  1. Auto-merge can be waiting while everything looks finished.

    One pull request stayed open because the agent's commit email wasn't tied to a GitHub identity. The repository's attribution rule held it. Using my GitHub noreply address fixed the attribution. I now distinguish requesting a merge from seeing that it has happened.

  2. Permissions were part of the deployment work.

    The production checkout needed the right owner, and the deploy user needed Docker access. Fixing those let the script run without interactive sudo prompts. An agent can't finish an unattended deployment if the underlying script is still waiting for a terminal.

  3. Each job needs a check suited to its result.

    For a message, I look for the outgoing record in Messages. For a release, I check the merged change, the containers, and the public response. These checks answer different questions. Keeping them separate makes failures much easier to track down.

What I'd improve next

First, check that the live AI News page contains the expected briefing date after deployment. Then make the morning schedules handle daylight saving time without a manual adjustment. Health trend charts can follow once there's enough history to make them useful.
