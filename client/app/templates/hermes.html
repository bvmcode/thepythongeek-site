My Personal AI Agent — A Chief of Staff on a Tailnet

One EC2 box, one gateway, every device I own — and an agent that runs the infrastructure of my life: my health records, my family's morning messages, my job-hunt pipeline, and the deploy pipeline of my production web site.

Built with Hermes Agent, an open-source agent framework by Nous Research. Provisioned with Terraform, private by default behind Tailscale, and driven from Telegram, my Mac, and the Claude-style terminal — wherever I happen to be.

  • One replaceable box Ubuntu 24.04 on a t3.medium. Terraform builds it. SSH never listens.
  • A private mesh Tailscale joins the agent, my Mac, my phone, and the production site.
  • Two jobs that finish A 6:00 AM note and a 9:00 AM job scout. Failures show up as failures.
  • Deploys with proof Branch, PR, merge, rebuild. The public site answers HTTP 200.

Why a personal agent (and why Hermes)

Every assistant I've used lives in someone else's sandbox. It can chat, but it can't touch my machines, remember anything meaningful between sessions, or wake up on a schedule. That's a toy. A hosted chatbot can be charming and still forget the reading I logged yesterday, refuse to touch the machine that actually sends the text, and go quiet at 6:00 AM because nobody gave it a clock.

What I wanted was a chief of staff: a process on a box I provisioned, with tools, a schedule, and a memory that survives the session.

  • Persistent memory It knows my health history, my contacts, my preferences. It does not meet me again from zero every morning.
  • Real tool access Shell, files, git, HTTP. An agent is only as capable as what it can do, and chat is not a tool.
  • A messaging gateway, not an app I talk to it from Telegram on my phone and from a desktop app on my Mac. A new platform is configuration, not a rewrite.
  • Scheduling Cron jobs that do things, not reminders. Send the message. Run the script. Deliver the report.
  • Skills it writes itself Every procedure it learns becomes a reusable, reloadable skill. The next session starts with the last one's hard-won steps already written down.

Hermes Agent checks every box, and it adds one I didn't think to ask for: it works with any model provider. Mine points at a local Ollama relay on the same box, so the weights stay remote while the agent, the files, and the cron stay mine. The brain is swappable. The chief of staff is not.

How I actually use it

Five jobs. All of them run. None of them is a demo prompt.

Health tracking

I dictate numbers mid-sentence ("172/110, sugar 320, 285.4 lbs"). It parses them into a real SQLite schema, mirrors them to CSVs on my Mac, and confirms. Diabetic logging that takes five seconds, with a row I would trust later.

Family comms

Every morning at 6:00 AM it texts my wife a Bible-verse note signed "I love you, Barry," rotating the verse each day. When I say "text Vic," it means it — and delivery is checked from her side of the Messages database, not from the agent's optimism.

Job hunt

A daily 9:00 AM scout combs remote job boards for senior and lead data-engineer roles with a stated salary of at least $150K. It verifies each posting is still live, drops anything already sent, and delivers a curated list to my phone.

Site deploys

"Push this fix" becomes a branch, a commit, a pull request, an auto-merge, the deploy script on the production box, and a health check. Done means the public site answered, not that the agent said it tried.

Voice

Voice notes in get transcribed. Replies talk back. On the desktop, a full-duplex realtime session lets me interrupt while the agent does the actual work behind the voice and answers in speakable prose.

The stack

Nothing on this box is meant to be reached from the public internet. Telegram is the front door I already carry. The Mac, the phone, and the production site sit on a Tailscale mesh, and the agent sits in the middle of it — gateway, scheduler, and the only place secrets live.

Tailscale mesh

Telegram The phone client. Job-scout deliveries and failure alerts land here.
Mac Messages, Calendar, and the health CSVs. The agent reaches it by SSH.
iPhone On the tailnet, so the mesh includes the device I actually have in my pocket.
mysite Production. docker compose, nginx on 443, and one deploy script.
EC2 “hermes” t3.medium · us-east-1 · the only machine the agent runs on
  • Terraform-provisioned, SSM-only shell. No public SSH.
  • Hermes gateway, dashboard, and cron scheduler.
  • Ollama relay to a cloud model. The weights stay remote.
  • ~/.hermes/.env holds secrets. An auth pool covers git and the clouds.

1 Provisioning — Terraform first, always

The instance is not a hand-built pet. The infrastructure repo (bvmcode/my-hermes-agent) defines it, and I want to be able to throw the box away. If I lose it, terraform apply and first-boot user-data rebuild the same shape: Ubuntu 24.04, a t3.medium, an encrypted gp3 root volume, IMDSv2 enforced, and SSH off. Shell access is SSM Session Manager. The user-data installs Hermes, writes one-time dashboard credentials, and starts the dashboard on :9119. Those five to ten minutes on first boot are the install. They are not a ritual I want to repeat by hand. 

cd infra
cp terraform.tfvars.example terraform.tfvars && cp backend.hcl.example backend.hcl
terraform init -backend-config=backend.hcl
terraform apply        # ~5-10 min of user-data install on first boot
Private by default. Port 9119 starts open only so the dashboard can be reached while Tailscale comes up, narrowed by dashboard_allowed_cidrs. Once the mesh is healthy that list is set to []. The dashboard, the agent, and every automation live only inside the tailnet. The public internet sees a box that answers nothing.

2 The tailnet — one mesh, every device

Tailscale joins the EC2 box, my MacBook, and my phone into one private mesh. All real inter-machine flows travel there. The key design is deliberately dull: a dedicated ed25519 key, installed with a one-liner, revoked by deleting one line from authorized_keys. No shared password. No account-wide token sitting on the agent just so it can reach my laptop.

Desktop to the gateway

The desktop app talks to the agent over the tailnet. Dashboard CIDRs are closed to zero, so that path is the path. There is no leftover public hole "just in case."

Agent to the Mac

The agent reaches the Mac over ssh <user>@<tailscale-ip>. That is how iMessage gets sent and how the health CSVs land in ~/Documents/HealthData/.

Production, pinned

mysite got the same treatment through one interactive SSH session: a repo-scoped key, the host key pinned, an alias recorded. After that, ssh mysite goes anywhere the deploy needs to go.

3 Health tracking — dictate, parse, mirror

I do not open an app and tap through a form. I say the numbers in the middle of a sentence, and the agent is responsible for turning that into a row I would trust later. That only works if the schema is strict and the agent is forbidden from guessing.

  1. Dictate A blood pressure, a glucose, a weight, dropped into an ordinary sentence.
  2. Parse into SQLite Source of truth. Typed columns, not a notes field pretending to be a database.
  3. Mirror the whole CSV After every insert, a full-state copy lands on the Mac. Updates and deletes travel too.
  4. Stay in its lane A dangerous reading gets one plain warning and a pointer to my provider. Then it stops.

The schema is deliberately diabetic-shaped. Two tables, because the log I actually keep is glucose, blood pressure, weight, and what I ate. The check constraint on glucose_type is there so a sloppy phrase cannot invent a category the later charts would quietly lie about. 

CREATE TABLE daily_readings (
    reading_date TEXT, taken_at TEXT,
    weight_kg REAL, glucose_mg_dl INTEGER,
    glucose_type TEXT CHECK (glucose_type IN
        ('fasting','before_meal','after_meal','bedtime','random')),
    systolic INTEGER, diastolic INTEGER, pulse INTEGER, notes TEXT
);
CREATE TABLE meals (
    meal_date TEXT, meal_type TEXT, eat_time TEXT,
    description TEXT, calories INTEGER,
    carbs_g REAL, protein_g REAL, fat_g REAL,
    fiber_g REAL, sugar_g REAL, notes TEXT
);

The mirror is the part most demos skip. SQLite stays the source of truth. A sync script pushes a full-state CSV mirror to ~/Documents/HealthData/ on my Mac after every insert — id-keyed, idempotent, and rebuilt whole each run. Rebuilding is slower than appending, and it is the version that stays correct the first time I fix a row. Append-only mirrors look fine until that correction. 

/usr/bin/python3 /home/ubuntu/health_data/health_sync.py
# synced: daily_readings=1, meals=6
The agent never invents a number. Values come from me or from a verified nutrition label. Packaged foods get looked up and the serving size gets checked. Quantities only I know are asked once, with calorie-anchored options. A fabricated row in a medical record poisons the whole picture, so the rule is absolute.

And the record-keeper knows its lane. When a glucose lands above 300 or a blood pressure hits crisis range, it says so once, plainly, and points at my provider. Then it shuts up. A health log is not a clinic, and it should not improvise one.

4 Scheduled automations — cron as a worker, not a bell

A reminder that says "text your wife" is not the job. The job is the text, the proof it landed, and the health mirror riding along afterward. The scout has the same standard: a list of links I have already seen, or links that 404, is worse than no list at all. So both jobs do the work, then report.

Daily · 6:00 AM

Love note

Composes a fresh Bible-verse note, rotating the book, and sends it to my wife's iMessage signed "I love you, Barry." Then it verifies delivery from the Messages database and syncs the health mirror.

Daily · 9:00 AM

Job scout

Hits remote-job sources and keeps senior or lead roles with a stated salary of at least $150K. Every posting is checked live, deduped against a seen-set, and what survives is delivered to Telegram.

Failures arrive as failures. The delivery target is my Telegram chat. Silence is not a success state. One honest limitation: both anchors are UTC-based, so the US spring daylight-saving change is a known drift they will need nudged. Automation I can reason about beats a scheduler whose clock I cannot explain.

5 The iMessage bridge — reach in, verify out

iMessage cannot be reached from Linux. Every bridge runs on a Mac, so the agent crosses the tailnet into mine and treats "sent" as a claim that still has to be proven. Send and verify are separate steps on purpose. The thing that transmits the message does not get to grade its own homework.

  1. Resolve the recipient from Contacts The real Contacts app, not a string I typed once. Digit-normalization means (856) 237-… and +1856… resolve to the same person. I should not have to remember E.164 to text my wife.
  2. Resolve the 1:1 chat, and refuse the rest The chat id pattern is any;-;<phone>. Anything that merely contains the person — a group chat included — is not a send. Close is not correct.
  3. Send with a small AppleScript Transmission only. The script does not read the database back, and it does not decide whether the send worked.
  4. Verify in the Messages database Read the SQLite store on the Mac and decode the attributedBody typedstream blob: the exact sent string, the is_from_me flag, and a seconds-old timestamp as proof.
The same gate, every time. Exact recipient, exact text, my confirmation — then done. A human-directed send does not get a shortcut because the last one went fine.

6 The deploy pipeline — from repo to production, agent-driven

This is the piece I use most. thepythongeek.com runs on a small Ubuntu box: docker-compose v1, nginx on 80 and 443, a uWSGI app container, long uptime, and one deployment script. The loop is boring on purpose. The interesting part is that the agent can run the whole thing, and that every step leaves evidence somewhere other than the agent's own log.

Credential design

One repo, one key

An ed25519 deploy key with read and write on a single repository. Nothing account-wide. A leaked key is a bad day for one repo, not for the GitHub user.

gh, once

The GitHub CLI was authenticated with a device-code flow. I got a code, approved it in a browser, and the OAuth token lives in the agent's credential store.

No sudo on the box

The production host got its own key in one interactive session. The repo directory was chowned to my user, and docker group membership replaced every sudo in the deploy path.

The loop

  1. BranchWork happens in the agent's clone.
  2. PushThrough the deploy key, not a personal token.
  3. MergePull request, then squash auto-merge.
  4. Deployssh mysite runs the script.
  5. VerifyContainers recreated. HTTP 200.
# 1. work happens in ~/repos/<site> (the agent's clone)
git checkout -b fix/<thing>
# ... edit ...
git commit -m "..."
# 2. push through the deploy key
git push -u origin fix/<thing>
# 3. PR + auto-merge through gh
gh pr create --base main --title "..." --body "..."
gh pr merge <n> --auto --squash
# 4. deploy on the box
ssh mysite 'sh ~/deploy.sh'   # git pull + docker-compose up -d --build
# 5. verify
docker ps                     # containers recreated
curl -s -o /dev/null -w "%{http_code}" https://thepythongeek.com   # 200

What the first day actually proved

  • Two pull requests, merged Authored, pushed, and merged — one instantly by repo auto-merge, one after it armed. The merged file was checked in the working tree after git pull, not trusted from the GitHub UI alone.
  • The production box rebuilt Image rebuilt, and nginx, app, and redis all recreated and up in seconds. The public site answered HTTP 200 through real TLS.
  • The ruleset held the line The repo carries a branch ruleset: no branch deletion, no force-push, pull requests required. That ruleset is where the agent learned the lesson below.

Commit identity is a security feature. The ruleset's require_extra_approval_for_unattributed_changes silently held the auto-merge open because the agent's commits carried a custom email with no GitHub identity behind it. The fix: commit as the owner's <id>+<username>@users.noreply.github.com, so every push is attributed and auto-merge fires the way it did on the first try.

7 Voice — STT in, TTS out, and the realtime layer

Voice is a transport. The agent still does the work. Talking to it does not create a second, weaker agent that can only chat — a request that needs tools is handed to the same agent that has the shell, the files, and the tailnet.

Voice in

Telegram voice notes auto-transcribe with local faster-whisper in the gateway's virtualenv. When that path was missing one dependency and failed, the same transcription ran locally: bundled ffmpeg, WAV, whisper, and the text fed straight back in. The fallback is the same pipeline, not a shrug.

Voice out

OpenAI TTS is the provider. Opus out, voice chosen in config, with per-message tone steering. It is the same engine the desktop's live mode uses, so a spoken reply and a live session do not sound like two different products.

Realtime, on the desktop

A full-duplex gpt-live session over WebRTC. It listens while it speaks, and I interrupt freely. Every request that is real work delegates to the agent, which runs the tools and streams the answer back as speakable prose.

8 Lessons this system taught

A weekend of wiring this up was mostly a weekend of finding out where "it worked" was a lie. The checks that mattered were never the ones the agent reported about itself.

  1. Where a check runs matters more than the check. A send is not real until the target system's own store confirms it. That is the Messages database, the merge state, or an HTTP status read from outside the box that just deployed.
  2. Cloud browser TTLs are a real constraint class. Free-tier sessions die in minutes. An automation that needs a human in the loop either fits inside a burst or waits for a persistent-profile tier. There is no third option where the session politely stays up.
  3. Anti-bot layers differ per site. Cloudflare's interstitial needed a click. GitHub's wall was a host-key fetch. Reddit rejects non-browser user agents at the proxy. DoorDash and Uber freeze synthetic input at the identity widget. There is no one stealth pass. Expect one fight per vendor.
  4. Strict-origin credential stores are correct, even when annoying. The vault refused a login saved for doordash.com when the page was identity.doordash.com. That is the right behavior. The fix was saving the entry for the actual auth host.
  5. Attribution is not bureaucracy. Repo rulesets enforce commit identity. The agent's commits should belong to a real identity — for the audit log, for auto-merge, and for the simple question of who pushed this.
  6. The boring wins: chown, groups, and one-liners. Half of "deployment automation" was removing sudo from a script by fixing ownership the right way, once. The clever half did not matter until the file permissions did.

9 What's next

The rails are already there. What is left is the work that needs either more data or a browser session that does not evaporate.

Trend charts

Glucose, blood pressure, weight, and calories from the health database, delivered as attachments. This waits on a week of rows so the chart is a trend and not a single point.

More daily tasks

New updates riding the cron that already fires, reports failures, and knows the difference between a schedule and a reminder.

DoorDash and Instacart

Behind a persistent-profile browser tier: log in once, fill a cart from a sentence, and leave checkout to a human. A free-tier session will not survive that.

A shopping list

Keyed to the meal log. What I have eaten, what is running low, drafted once a week instead of reconstructed from memory in the store.
